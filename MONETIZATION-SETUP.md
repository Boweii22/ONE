# ONE monetization activation

Live: RewardedAds.kt loads consent, requests an AdMob rewarded ad through RevenueCat, and reports only a server-verified reward. It is wired into a "WATCH AN AD" choice in the challenge sheet, gated on `BuildConfig.ADMOB_REWARDED_UNIT_ID` being non-blank (real IDs are set in `local.properties`) and on `take_ad_bypasses_remaining_today > 0`. The checkout endpoint validates a Supabase user and constructs an identified RevenueCat Funnel URL; the website has a Google sign-in flow (Supabase OAuth, `/auth/v1/authorize?provider=google`) and a "BUY ONE CREDITS" button that calls it, live in production at oneis.live.

## AdMob
1. Add ONE as an Android app with package com.tomribowei.one. Link its Play listing.
2. Create a Rewarded ad unit called Cooldown skip. Send the app ID (contains ~) and ad unit ID (contains /).
3. Configure Privacy & messaging for applicable consent regions. Enable impression-level ad revenue.
4. In the AdMob console, set this rewarded unit's server-side verification callback URL to https://api.revenuecat.com/v1/incoming-webhooks/admob-ssv-rewarded — this is RevenueCat's own verification endpoint; AdMob calls it directly, not our backend.
5. In the RevenueCat dashboard, create a virtual currency with code `ADTAKE`. Under Ads → Rewards, add a rule for this ad unit that grants **1 `ADTAKE`**. RevenueCat verifies the reward against AdMob's signature and credits the currency itself; the app cannot mint it.
6. Server-side redemption: the app calls the `redeem-ad-reward` Edge Function (not the RPC). It spends 1 `ADTAKE` through RevenueCat's REST API v2 (`POST /projects/{id}/virtual_currencies/transactions`, idempotent per request) and only then calls the service-role-only `grant_verified_ad_bypass`. `bypass_take_refill('ad')` is refused for clients. Set these Edge Function secrets: `REVENUECAT_SECRET_API_KEY` (v2 secret key, read+write on customer configuration and customer purchases), `REVENUECAT_PROJECT_ID`, optional `REVENUECAT_AD_CURRENCY_CODE` (default `ADTAKE`). Run migration `202609260001_verified_ad_bypass.sql` and deploy the function.
6. The `skip` reward is already separate from ONE Credits at the schema level (`take_ad_bypasses_used_date/count` on `profiles`, not the credit ledger) — an ad can never mint purchasable wallet balance.

Done: idempotent redemption RPC (`bypass_take_refill`, replacing the earlier retired `grant_ad_skip`), daily cap (`app_settings.take_ad_bypass_daily_cap`, default 2/UTC day), consumption tied to a real refill-in-progress check (not merely opening the challenge sheet), and a failed-load fallback to the normal credit/wait choices (see `RewardedAds.kt`'s existing status callback). The client-observed `rewardVerificationCompleted`/`verifiedReward` check in `RewardedAds.kt` is the correct, trustworthy signal here — RevenueCat has already verified the reward server-side against AdMob before ever reporting it back to the SDK, so there is no separate webhook or custom verification endpoint for us to build. The only remaining step is confirming steps 4-5 above are actually configured in the AdMob console and RevenueCat dashboard, and testing a real ad unit end to end on a physical device (Google's sample/test ad units cannot exercise RevenueCat's SSV path).

Real rewarded units commonly return "no fill" on a device AdMob hasn't registered as a test device — that's anti-fraud protection, not a bug. Set `ADMOB_TEST_DEVICE_IDS` in `local.properties` to a comma-separated list of device hashes (find yours in logcat: "Use RequestConfiguration.Builder().setTestDeviceIds(...) to get test ads on this device") and `OneApplication.onCreate()` registers them via `MobileAds.setRequestConfiguration(...)` — but only in debug builds (`BuildConfig.DEBUG`), so leaving the property set can never leak test device IDs into a release build. A brand-new AdMob account/app can also sit in review for a period before serving any ads at all; check for an account or app status/approval banner in the AdMob dashboard before assuming a fill problem is a code bug.

## RevenueCat Funnels
1. Connect Stripe Billing (or RevenueCat Billing) as a web configuration in the existing ONE project.
2. Follow `ECONOMY.md`: create/import Spark (3 ONE Credits), Challenger (20), and Headliner (50). One credit buys one successful cooldown skip; a normal takeover is free. Add them to a `credits` offering. Keep any already-reserved `one_tickets_*` Android IDs as legacy aliases rather than recreating them.
3. In Funnels, create a purchase flow with the offering and a confirmation page. Publish a sandbox URL first and send it to me, along with exact web product IDs. Send the production URL after sandbox testing passes.
4. Configure the existing Supabase `revenuecat-webhook` function with the webhook authorization secret privately and an exact product-to-credit map in `ONE_PRODUCT_CREDITS`. Copy every Android and web product ID from the dashboards. The function now fails closed when this map is absent instead of trusting aliases.
5. The website's Google sign-in (Supabase OAuth) and POST /api/checkout (which requires that authenticated access token) are now implemented in code. You still need to enable the Google provider for this Supabase project in Authentication → Providers, and add this site's URL to the provider's authorized redirect URIs. Never take the account ID from an input field.
6. Test a sandbox payment, cancelled payment, duplicate webhook, and delayed webhook. Verify the correct account receives credits exactly once. Only then set `ONE_WEB_CHECKOUT_ENABLED=true` and `REVENUECAT_FUNNEL_URL` to the production base funnel URL.

The Android app does not currently link to web checkout. A mobile purchase link requires a separate review of the applicable Play program and region before enabling it.
